# new-api 前端订阅版 Demo 改版分析

## 文档范围

本文记录对新版 HTML Demo 与当前 `new-api` 的只读对比，供后续确认改版范围使用，不代表已经批准的实施方案、正式价格或业务承诺。

- Demo 文件：`ZYY-AI-订阅版(2).html`。
- 对比代码基线：`8d49ff894`（`Merge branch 'zyy-b' into zyy-c`）。
- 检查方式：阅读 Demo 源码，在浏览器检查模型页及订阅页，对照当前前端及相关接口、模型。
- 验证限制：未启动当前系统进行完整运行态对比；本文“现状”以源码为准，不代表线上实际配置。

## 一、总体结论

这份 Demo **不只是给当前 new-api 换皮，而是把“通用 API 网关控制台”改造成“面向普通用户的订阅积分产品”**。

改动可以分成三类：

1. **界面重构**：导航、布局、模型页、日志、看板等。
2. **使用流程重构**：新手引导、单模型密钥、统一注册登录、订阅购买。
3. **业务机制变更**：永久积分、GPT 专项积分、订阅权益排期、自动续费、邀请奖励、发票。

其中第三类无法仅靠前端完成，是本次改版最需要提前拆清楚的部分。

## 二、整体结构与导航改动

### 2.1 顶部导航重新组织

Demo 顶部固定为：

**首页｜模型｜订阅｜配置教程｜邀请好友〔赚积分〕｜账号入口**

相较当前实现，需要：

- 统一公共页面与登录后页面的顶栏表现。
- 将“模型”作为未登录用户的默认落地页。
- 将登录后的“首页”变为用户工作台，而不是当前宣传首页。
- 新增独立的“订阅”“配置教程”“邀请好友”入口。
- 将邀请入口做成带图标、暖色徽标的突出入口。
- 增加账号菜单中的积分余额、当前订阅、续订操作。

当前顶栏还支持后端动态导航配置，改版时需要明确：**保留配置能力，还是限定用户端菜单结构**。

### 2.2 工作台侧栏重新分组

| 分组 | Demo 内容 |
| --- | --- |
| 常用 | 新手引导、API 密钥、使用日志、任务日志、数据看板 |
| 个人 | 积分钱包、我的订阅、个人资料 |
| 系统 | 安全与访问、审计日志 |

当前已有大部分基础模块，但需要：

- 新增独立“新手引导”。
- 新增用户侧“我的订阅”。
- 将安全、审计菜单重新归组。
- Demo 未展示当前的 Playground、聊天等入口，需要确定隐藏还是保留。

**特别注意：当前 `/subscriptions` 是管理员套餐管理页面，不应直接拿来替换成用户“我的订阅”。**

### 2.3 页面间返回逻辑变化

Demo 实现了带来源的任务导航：

- 从钱包进入积分明细，再返回钱包。
- 从新手引导进入订阅，再返回原引导步骤。
- 从个人订阅进入订单、方案等页面。
- 返回时恢复滚动和部分上下文。

正式实现应复用当前 TanStack Router，而不是照搬 Demo 的 hash 路由与 DOM 显隐逻辑。

## 三、按页面梳理具体改动

### 3.1 模型页：从技术价格目录转为选购页面

当前已经有模型广场、搜索、筛选、表格/卡片、详情抽屉等能力。Demo 的变化主要是：

| 项目 | Demo 目标 |
| --- | --- |
| 页面表达 | 强调“模型适合做什么”“一元大概能用多少次” |
| 分类 | 按国内、海外及厂商分组 |
| 价格展示 | 官网参考次数、平台次数、折扣、节省比例 |
| 转化操作 | “使用此模型”进入创建密钥流程 |
| 开放状态 | 部分海外模型仅展示，标注暂不开放 |
| 视频模型 | 单独展示，按时长口径报价，不套用文本次数 |

另外新增：

- 页首折扣宣传区。
- 固定估算口径：每次输入 2,000 / 输出 500 token。
- 明确次数只是参考值。
- 视频模型的待接入、价格待定状态。

**不是简单换表头**：当前价格受到模型、分组、计费类型等影响，不能直接把 Demo 的静态价格和模型清单变成真实配置。“低至几折”等宣传也必须来自可核验的数据。

### 3.2 新手引导：新增独立三步流程

Demo 的流程：

**创建密钥 → 准备积分 → 接入我的应用**

需要实现：

- 步骤导航、上一步/下一步。
- 当前密钥与积分状态提示。
- 引导内选择订阅。
- 接口地址、模型名、密钥复制。
- 客户端配置、curl、Python 示例。
- “稍后再看”“结束引导”。
- 完成后默认进入 API 密钥页。

当前概览已有接入引导相关代码，但 Demo 是完整的任务流程，属于**扩展重做，而非从零新增所有能力**。

### 3.3 API 密钥：由高级令牌管理转为单模型接入

最明显的行为变化是：

> Demo 每个密钥绑定一个模型。

当前密钥支持模型限制列表、分组、Auto 分组、IP 限制、有效期、批量创建等高级能力。

Demo 则聚焦：

- 名称、密钥、状态、绑定模型筛选。
- 创建时选择一个模型。
- 列表展示密钥额度、已用额度、进度条。
- 复制名称、完整密钥、模型 ID。
- 编辑、启停、删除。
- 创建成功后的接入引导。

需要提前确定：

- 单模型只是普通用户界面的约束，还是后端也强制？
- 现有多模型密钥如何显示、编辑？
- 高级配置隐藏到“高级设置”，还是不再对普通用户提供？
- 密钥额度如何转换为积分展示？

**不建议因为新版界面简化，就直接破坏已有多模型密钥及高级调用方式。**

### 3.4 积分钱包：结构和业务语义都变化

当前钱包把余额、充值、兑换码、订阅套餐、邀请奖励放在一起。

Demo 将其拆成：

- 钱包：看积分余额与流水。
- 订阅：购买及订单。
- 邀请：活动与奖励。

钱包新增四个核心指标：

1. 已到账积分总额。
2. 通用积分。
3. GPT 系列专项积分。
4. GPT 专项积分待释放。

同时增加：

- 按来源查看积分构成。
- 独立积分明细页。
- 日期筛选。
- 到账、消耗、奖励、退款等流水类型。
- 通用积分与专项积分使用范围说明。

**关键差异**：当前主要是账户 `quota`、邀请 `aff_quota` 等额度；Demo 是带来源和模型适用范围的多类积分账户，不能只做显示单位替换。

### 3.5 订阅方案：从钱包内套餐卡升级为独立交易中心

Demo 有三档月付和三档年付：

| 档位 | 月付价格 / 到账积分 | 年付价格 / 到账积分 |
| --- | --- | --- |
| 入门 | ¥29 / 29,000 | ¥290 / 348,000 |
| 标准 | ¥89 / 89,000 | ¥890 / 1,068,000 |
| 专业 | ¥199 / 199,000 | ¥1,990 / 2,388,000 |

页面需要：

- 月付、年付同页对比。
- 每档支持单次购买和自动续费。
- 展示本次支付、到账积分、服务周期。
- 区分首次购买和后续自动续费赠送。
- 购买确认弹窗。
- 订阅服务、订单、发票三个分区。
- 当前订阅及权益排期。

以上价格是 **Demo 设定，不能默认当作已经批准的正式价格**。

### 3.6 我的订阅：新增用户侧管理页面

需要展示：

- 当前生效档位。
- 当前服务到期时间。
- 手动续订入口。
- 自动续费方案、支付方式、预计扣款时间。
- 取消自动续费。
- 暂停保留、等待生效的权益。
- 跳转订阅订单和方案页面。

这一页和当前管理员的套餐 CRUD 是两个不同模块。

### 3.7 邀请好友：由简单邀请奖励变为活动体系

当前主要是邀请码/链接、邀请额度和转余额。

Demo 增加了：

- 公开活动页与全部活动列表。
- 我的邀请链接、邀请码。
- 有效好友人数与档位进度。
- 我的好友。
- 奖励结算记录。
- 已到账、待释放奖励。
- 我的邀请人补录，一次绑定后锁定。

对应的新规则包括：

- 有效人数 0—2、3—8、9 人以上，对应 5%、7%、10%。
- 订单支付时锁定活动版本及比例。
- 满 7×24 小时后释放。
- 好友复购也产生奖励。
- 奖励为 GPT 系列专项积分。
- 退款影响未释放奖励。
- 活动调整不追改历史订单。

**这是新业务子系统，不是把当前邀请卡片放大成一个页面。**

### 3.8 注册登录：入口和认证方式都变化

当前已有账号密码、OAuth、微信验证码、Passkey 等能力。

Demo 改为统一弹窗：

- 微信扫码。
- 邮箱验证码。
- 手机号验证码。
- 未注册账号验证后自动注册。
- 邀请码常显，并支持从链接带入。
- 登录后恢复原购买、邀请等任务。

需要特别区分：

- 当前微信验证码流程，不等于真实扫码确认登录。
- 邮箱注册验证码，不等于邮箱验证码直接登录。
- 手机号登录还涉及短信服务和账号绑定体系。
- 旧账号如何与手机号、微信身份合并，不能靠前端判断。

Demo 中二维码、验证码和登录状态都是模拟逻辑，不能直接移植。

### 3.9 使用日志、任务日志、审计日志：主要是重排与口径适配

这三块当前均已有基础能力，不应误判为全部新增。

#### 使用日志

- 主列表突出模型、token、消耗积分。
- 详情保留完整参数和参考费用。
- 重新设计筛选栏、表格与详情抽屉。
- 核对积分与当前扣费日志的映射。

#### 任务日志

- 继续覆盖任务及绘图记录。
- 统一筛选、状态、结果与详情样式。
- 保留现有任务结果和产物访问能力。

#### 审计日志

- 重排为账号管理操作视角。
- 支持分类、结果、来源 IP、详情。
- Demo 有 CSV 导出，需要核对现有导出能力及权限。
- 核对 Demo 分类是否能映射现有事件类型。

### 3.10 数据看板：从综合分析简化为个人用量分析

Demo 聚焦：

- 请求总数。
- 参考费用。
- token 总量。
- 平均 TPM。
- 本月花费。
- 最常用模型。
- 最烧钱密钥。
- 消耗趋势。
- 模型调用分布。

当前已有较丰富图表和指标，主要工作是：

- 精简普通用户界面。
- 复用已有统计和图表能力。
- 增加或核对按密钥的费用排行。
- 区分自然月统计与近 7/14/30 天统计。
- 明确参考费用与实际扣积分的关系。

### 3.11 个人资料、安全与访问

#### 个人资料新增或调整

- 头像上传、恢复默认。
- 昵称。
- 登录邮箱。
- 手机号绑定与更换。
- 发票抬头。

其中手机号、头像存储、发票信息不能假设现有资料接口直接支持，需要扩展或另接接口。

#### 安全页

Demo 主要展示手机号、登录设备、注销账号。

当前实际上还有：

- 密码管理。
- 账号绑定。
- 登录会话。
- 个人访问令牌。
- Passkey。
- 2FA。
- 隐私设置。

**新版 Demo 展示得更少，不等于应该删除已有安全能力。** 建议保留，通过分组或高级入口收纳。

### 3.12 配置教程、客服、发票

#### 配置教程

新增站内教程视图：

- 创建密钥、准备积分、接入应用。
- Codex CLI / WorkBuddy。
- curl、Python。
- 接入验证、常见报错。
- 积分、订阅、邀请规则。
- 客服入口。

现有文档站与站内教程需要划分维护边界，避免重复且内容不一致。

#### 客服

统一客服弹窗与各业务入口。

#### 发票

Demo 包含申请、记录、进度、下载，以及实际支付金额口径和最低申请金额规则。已检查的相关路由中未看到对应完整开票能力，不能视为现成接口。

## 四、真正超出“前端改版”的核心改动

| 业务项 | 当前与 Demo 的主要差异 | 影响 |
| --- | --- | --- |
| 永久积分 | 当前订阅有独立额度、到期和重置机制；Demo 积分到账后永久保留 | 账户与扣费模型 |
| 双积分账户 | 通用积分与 GPT 专项积分分开，且通用优先 | 模型识别、预扣、结算、退款 |
| 订阅权益排期 | 同档顺延，升级暂停低档，降级排队 | 权益状态机 |
| 自动续费 | 授权不等于支付；扣款成功才赠 10% | 支付渠道、回调、幂等、撤销授权 |
| 邀请结算 | 支付锁比例、7 天释放、退款取消 | 奖励账本与定时结算 |
| 统一验证码登录 | 验证后登录或注册，支持多身份 | 认证与账号合并 |
| 发票 | 可开票额度、申请、状态、文件 | 开票后台或第三方集成 |

其中最重要的是：

> Demo 将“积分余额”和“订阅服务期限”彻底分开。当前订阅额度机制不能未经改造就承接这一承诺。

另外，Demo 宣称“单次最低 1 积分、四舍五入、不部分扣减、不透支”，这涉及真实计费与流式请求结算，不能只改文案。

## 五、建议的实施拆分

### 第一阶段：只重构用户端界面，保留现有业务

- 顶栏、侧栏、主题与响应式。
- 模型页布局。
- 密钥列表与创建流程。
- 新手引导。
- 日志、看板、个人资料的展示重构。
- 配置教程及客服入口。

这一阶段可以先取得大部分视觉效果，风险相对可控。

### 第二阶段：订阅与积分体系

先明确永久积分、旧余额迁移、权益排期及扣费规则，再实现：

- 双积分账户与流水。
- 用户订阅中心。
- 单次购买。
- 自动续费授权、扣款与赠送。
- 历史订单兼容。

### 第三阶段：邀请、认证、发票

这些模块有各自独立的外部依赖和风控要求，建议分别实施，避免与视觉改版一次性混在一起。

## 六、待确认的关键边界

1. **是先做到“长得像 Demo”，还是 Demo 的业务规则也全部落地？**
2. 单模型密钥是否强制，旧多模型密钥是否继续兼容？
3. 旧余额、旧订阅剩余额度、旧邀请奖励如何迁移？
4. 自动续费采用哪个实际支持签约扣款的支付渠道？
5. 现有聊天、Playground、Passkey、2FA 等能力是否保留入口？
6. 管理员后台是否保持现状，仅改普通用户端？

**建议：普通用户端按 Demo 重构，管理员后台保留；视觉改版与计费、订阅机制分阶段上线。** 这样既能明显改变产品体验，也更容易控制支付和历史余额风险。
